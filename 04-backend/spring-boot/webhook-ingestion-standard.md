# Webhook Ingestion and Security Standard

## Purpose

This standard defines the requirements for receiving, verifying, and safely processing inbound webhooks from external third-party services (e.g., Stripe, Twilio, SendGrid, GitHub, external ERPs).

Inbound webhooks are unauthenticated at the transport layer (they arrive over the public internet); **they must be treated with zero-trust validation before any payload data is processed or persisted.**

---

## 1. Webhook Lifecycle and Ingestion Pattern

Webhooks must never execute slow business logic or synchronous downstream API calls within the incoming HTTP request. Doing so risks timeouts, provider retries, duplicate transactions, and thread pool exhaustion.

```text
External Provider (e.g., Stripe)
         ↓ POST /api/v1/webhooks/{provider}
Inbound Webhook Controller
   ├─ Step 1: Verify HMAC Signature (timing-safe comparison)
   ├─ Step 2: Validate Timestamp (replay protection: age <= 5 min)
   ├─ Step 3: Check Deduplication (provider_event_id)
   └─ Step 4: Persist raw payload to `inbound_webhook_events` table (Status = 'RECEIVED')
         ↓
Immediate HTTP 202 Accepted (returned in < 200 ms)

         ↓ (Asynchronous)
Background Webhook Consumer Worker
   ├─ Deserializes & validates payload
   ├─ Executes business logic / transitions state in DB transaction
   └─ Marks event as 'PROCESSED' or 'FAILED'
```

---

## 2. Cryptographic HMAC Signature Verification

1. **MUST** verify the signature header (e.g., `Stripe-Signature`, `X-Hub-Signature-256`) against the configured webhook secret before parsing or deserializing the body.
2. **MUST** use a **timing-safe comparison** to prevent timing attacks:
   ```java
   // In Java / Spring Boot:
   boolean isValid = MessageDigest.isEqual(
       computedSignatureBytes,
       receivedSignatureBytes
   );
   ```
3. **MUST NOT** verify signatures against an already deserialized or formatted JSON object. Signatures must be computed against the **raw byte array** of the request body as received over the wire.
4. **MUST** return `401 Unauthorized` or `400 Bad Request` immediately if the signature does not match; never process payloads with invalid signatures.

---

## 3. Replay Protection

1. Extract the timestamp from the webhook header (e.g., `t=1731300000` in Stripe).
2. Compute the time drift:
   $$\Delta t = |t_{\text{current}} - t_{\text{header}}|$$
3. **MUST** reject any webhook where $\Delta t > 300\text{ seconds}$ (5 minutes) to protect against replay attacks.

---

## 4. Idempotency and Deduplication

Third-party providers guarantee at-least-once delivery; webhooks will be retried if network acknowledgments drop.

1. **MUST** store and index the provider’s unique event identifier:
   ```sql
   CREATE TABLE inbound_webhook_events (
       id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
       provider VARCHAR(32) NOT NULL,            -- 'STRIPE', 'TWILIO'
       provider_event_id VARCHAR(128) NOT NULL,  -- e.g. 'evt_1Mv...'
       event_type VARCHAR(64) NOT NULL,          -- 'payment_intent.succeeded'
       payload JSON NOT NULL,
       status VARCHAR(32) NOT NULL,              -- 'RECEIVED', 'PROCESSED', 'FAILED', 'IGNORED'
       retry_count INT UNSIGNED NOT NULL DEFAULT 0,
       error_message VARCHAR(512) NULL,
       received_at DATETIME NOT NULL,
       processed_at DATETIME NULL,
       UNIQUE KEY uq_provider_event (provider, provider_event_id),
       INDEX idx_status_received (status, received_at)
   );
   ```
2. If an incoming event has already been recorded in `inbound_webhook_events`:
   - Return `200 OK` or `202 Accepted` immediately so the provider stops retrying.
   - Do not re-execute the business logic.

---

## 5. Secret Storage and Rotation

1. Webhook signing secrets must be stored in the approved platform secret manager—never hardcoded in source code or `.env` files.
2. Support rolling secret rotation: when rotating a webhook secret, the validator should accept signatures generated by either the **new secret** or the **previous secret** during a 24-hour transition window.
